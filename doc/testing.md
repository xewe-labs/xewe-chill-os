# Testing

Two kinds of project tests, both run by `xewe test`: unit tests that need no board, and board tests
that run against a flashed board over serial. Run the tools as
`build/tools/.venv/bin/python -m xewe <command>` (below: `xewe`). Flags are in the
[tools command README](https://github.com/xewe-labs/xewe-os-tools/blob/main/src/xewe/README.md),
the runner in the tools' `src/xewe/testing/README.md`.

## Unit tests

They live in `tests/unit/` and run on the developer machine: `@pytest.mark.unit` Python, or C++
built with g++. The project's unit tests check source facts only, with no board and no build.

```sh
xewe test --unit-only
```

`xewe test -v` is verbose; pytest's own flags go after `--` (`xewe test -- -vv -k name`).

## Board tests

They live in `tests/board/`: pytest files that run against the board through `xewe test`. The
runner builds the firmware once per session, finds the board, flashes it once and hands each test
the session's serial console.

```sh
xewe test --chip c3 -- -m board
```

- Without a board, board tests are reported as `compiled, not run` and the command exits 0.
- `--require-board` turns a missing board into exit 4.
- `--no-board` compiles and never opens a port, even with a board plugged in:
  `xewe test --chip c3 --no-board -- -m board`.
- `XEWE_NO_BOARD=1` in the environment does the same for every command; use it for compile-only
  sessions such as CI and agents. `test` still compiles; `flash`, `run` and `serial` exit 4.
- `--no-flash` tests the firmware already on the board. `--module SLUG` selects a module's tests.
- Never pass `--erase` or flash a board unless asked: flashing keeps NVS, erasing does not.

Read the result from the exit code (0 ok, 1 failure, 4 board required but missing) and the pytest
summary; the line `compiled, not run: no board attached (...)` is not an error.

## The dotenv keys the tests use

The dotenv file is `.env` in the project, or in the tools checkout; you create it and nothing
writes it. Never open, print or copy it. The keys the tests and the board access read, names only:

- `XEWE_PORT`: serial port of the board (default: detected).
- `XEWE_CHIP`: chip of the board, `c3`, `c6` or `s3` (default: detected).
- `XEWE_TEST_DEFINES`: defines `xewe test` and `xewe flash` build and flash with when no
  `--define` is given.
- `XEWE_TEST_BUTTONS_PIN` and `XEWE_TEST_PINS_ADC_PIN`: pins for the buttons and pins module
  board tests.
- `XEWE_REQUIRE_BOARD`: `1` makes a missing board exit 4, as `--require-board`.

Other `XEWE_TEST_*` keys gate board tests of particular modules; the list is in the tools' dotenv
README (`src/xewe/env/README.md`, section Keys).

## CI

`.github/workflows/ci.yml` only calls the reusable workflows of xewe-os-tools, at the tag of
`[tools] ref` in `xewe.toml`:

- On every push to main and every pull request, the `build` job calls `xewe-build.yml` with
  `strict_lint: true`: it builds the firmware and runs the host tests.
- On a version tag `X.Y.Z`, the `release` job calls `xewe-release.yml`: it builds c3, c6 and s3,
  runs the release card check (`xewe release-card verify --ci`) and publishes the GitHub Release.
- The card is generated by `scripts/release.sh` from one recorded run (unit tests, the board
  tests of one chip, its build); see the header of `scripts/release.sh`.

## This project's tests

| File | Checks |
|---|---|
| `tests/unit/test_config.py` | The project's `Config.h`: the generated blocks, nothing active but the pad's overrides. |
| `tests/unit/test_fan.py` | Fan sources and `src/Fan/Config.h`; builds `test_curve.cpp` (the curve maths of `Curve.h`) with g++. |
| `tests/unit/test_mlx90614.py` | Mlx90614 sources and `src/Mlx90614/Config.h`; builds `test_convert.cpp` (`Convert.h`) with g++. |
| `tests/unit/test_pad.py` | PadWeb and the sketch: the declarations, the selection, the rate-limited strip calls, the license headers. |
| `tests/board/test_fan.py` | `$fan` on a flashed board: fans, settings, the curve, the fail-safe. |
| `tests/board/test_mlx90614.py` | `$mlx90614`: settings, address and pin checks, a bounded scan, a reading with a sensor attached. |
| `tests/board/test_pad.py` | `$pad`: colours, lights on/off against the led module, the offline fail-safe, restart. |
| `tests/MANUAL.md` | The first test on the assembled pad, by hand. |

Each board test file has a `test_compiles` that runs without a board; the rest are reported as
`compiled, not run` until a board is attached. The `XEWE_TEST_*` keys some of them need are named
in each file's docstring.
